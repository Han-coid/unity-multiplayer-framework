# 同步时序与延迟优化

版本补充：当前 0.8.0 示例协议已升为 6，默认启用可选基础预测，见 [基础移动预测与服务器校正](基础移动预测与服务器校正.md)。下文版本 2 描述的是 0.4.0 的原始时序改动；`TimingComparisonTest.ps1` 显式使用 Legacy，保留原对比口径，预测开关对比使用 `PredictionComparisonTest.ps1`。

原有时序方案提供基础时序优化和可重复测量。示例使用「响应优先 60 Hz」，仍然是服务器权威移动：客户端发送意图，服务器计算位置，远端角色通过 NetworkTransform 插值显示。0.7.0 增加本地预测、服务器校正和未确认移动输入重放；尚未实现动态物理回滚或射击命中补偿。

## 1. 先操作两个窗口

1. 重新构建 **Tools → Han Multiplayer → Build Windows Demo**；大厅使用 **Build Windows Lobby Demo**。旧 exe 不会因修改源码自动更新。
2. 两端连接面板都选择「响应 60」，再由一端创建主机，另一端通过 IP 加入。默认已选此配置。连接后按钮锁定；切换配置要两端断开重连。
3. 大厅需要全员准备并由房主开始游戏；点击「显示网络诊断」打开采集面板。基础示例默认显示面板，收起后可点击窗口右下角「展开网络诊断」。
4. 先保持角色静止约一秒，再按方向键起步。重复数次，观察「静止起步 → 本机位置响应」。Host 本地玩家不经过远端网络，应重点查看远端客户端。
5. 在客户端选择「中度」弱网后重复。延迟/抖动作用于该端发送方向，发送/接收丢包分别作用于该端收发；两端设置会叠加。测试结束点「恢复正常网络」。
6. 在本机导出 JSON，保留两端报告和配置，便于判断网络、主循环或插值问题。

人工对比可用同一启动脚本，关闭本轮两个窗口后再运行另一配置：

```powershell
.\scripts\Start-LobbyAcceptance.ps1 -TimingPreset Responsive60
.\scripts\Start-LobbyAcceptance.ps1 -TimingPreset Legacy30
```

## 2. 三种配置改变什么

| 配置 | NGO Tick | 输入发送 | 服务器移动 | 位置显示 |
| --- | --- | --- | --- | --- |
| 原版 30（基线） | 30 Hz | Update 最多 30 次/秒，随帧率量化 | FixedUpdate，采用项目原有物理步长 | 保留插值及额外 Lerp 平滑 |
| 对齐 30 | 30 Hz | NGO Tick | NGO Tick，固定 1/30 秒步长 | 保留插值及额外 Lerp 平滑 |
| 响应 60（示例默认） | 60 Hz | NGO Tick | NGO Tick，固定 1/60 秒步长 | 保留插值，关闭额外位置 Lerp 平滑 |

旧示例 Update 发送、FixedUpdate 移动和网络 Tick 各自排队，且位置附加平滑会增加跟随时间。本轮将输入发送与服务器模拟对齐 NGO Tick，模拟结果进入本次 NetworkTransform 采集周期。60 Hz 进一步缩短 Tick 间隔，同时会提高 CPU 和带宽开销。默认项目 Fixed Timestep 通常是 0.02 秒；本工具不改它。

响应 60 减少附加平滑后，弱网下的位置抖动可能更明显，可按游戏需求选择对齐 30 或自行调校平滑。

60 Hz 不等于每帧都能响应，也不能消除地理距离造成的传输耗时。设备主循环达不到目标频率时，追赶 Tick 可能集中在同一帧，不能按面板中的目标 Tick 推断画面流畅度。查看实际 FPS、帧耗时和实测发送 Hz。垂直同步可能覆盖 `Application.targetFrameRate`，工具不改变项目垂直同步设置。

`PositionLerpSmoothing=false` 关闭 NGO 的额外位置平滑，并没有关闭 `Interpolate`。配置中的 0.04 秒是该平滑算法启用时的参数，本配置关闭它，因此不能把这个数值理解成「固定 40 ms 插值缓冲」。工具不修改 NGO 静态插值 Tick 偏移。

## 3. 如何看耗时

| 指标 | 实际含义 |
| --- | --- |
| RTT | UTP 可靠管线的网络往返估计，没有估计时显示暂无 |
| 最新输入采样 → 发出 | 最近一帧输入样本到发送的本机间隔；持续刷新采样，不能代替按键事件排队耗时 |
| 输入采样 → 服务器应用确认 | 该输入参与服务器模拟后回执到达本机，包含发送、网络、服务端排队和回程 |
| 服务端排队 / 执行 | 收到该输入到参与模拟、以及该次模拟执行的服务器本地耗时 |
| 静止起步 → 本机位置响应 | 角色静止及零输入均至少 0.2 秒后，新移动输入到帧末观察到位置变化至少 0.02 米 |
| 实测服务端模拟 Hz | 回执带回服务器实际模拟频率；测量关闭或无回执时没有新观测 |

所有耗时采用本进程单调时钟，客户端不与服务器比较绝对时间戳。起步测量不包含键盘硬件、GPU 渲染、屏幕扫描延迟；其他来源的位移也可能触发阈值，因此是基础示例的诊断指标。它不保证适用于带传送、击退、复杂物理或外部移动脚本的游戏。超过两秒或中途松开输入会取消该次起步测量；持续移动不产生起步样本。

摘要最多保留最近 120 项，显示均值、最近秩 P95、数量及距最近样本时间。断线/暂停后应参考样本年龄，不能把旧值当成实时数据。导出报告包含 `timingMeasurements` 下的原始有界数组及摘要；比较分位数时从数组重算，不平均多个摘要的 P95。

「采集响应耗时」只在编辑器和 Development Build 生效。必须区分两条移动路径：

| 移动模式 | 网络通知 | 关闭采集 / 正式构建 |
| --- | --- | --- |
| Legacy 旧版移动 | 开发测量请求额外的不可靠回执，最多 10 次/秒/玩家 | 不再请求开发回执 |
| On / Off 预测输入协议 | 服务器发送确认序号和完整运动状态，测量复用此通知；默认 60 Hz 下定期约 20 次/秒，传送/校正/重新定基可额外发送 | 仅停止响应样本采集；维持游戏运行所需的权威同步 |

预测定期通知间隔为 `ceil(TickRate / 20)` 个 Tick，因此 30 Hz 配置下定期约 15 次/秒；不要把“约 20 Hz”当作包含所有事件通知的硬上限。两种模式的帧率和实际发送 Hz 都继续采集。丢包会减少可匹配确认，确认耗时不覆盖未收到的命令回执。

当前界面复选框仍显示「额外回执最多 10 次/秒/玩家」，这段提示只适用于 Legacy；本次文档修订没有修改运行时 UI。使用 On/Off 时按上表理解，不能用关闭测量验证“停止所有回执”。

## 4. 自动对比

先构建基础 Windows 示例，在项目目录 PowerShell 运行：

```powershell
.\scripts\TimingComparisonTest.ps1
# 或只测一种网络条件
.\scripts\TimingComparisonTest.ps1 -Profile Normal
.\scripts\TimingComparisonTest.ps1 -Profile Moderate
# 延长每组采集以增加起步样本
.\scripts\TimingComparisonTest.ps1 -DurationSeconds 60
```

脚本在本机依次启动 Host 和客户端，测试三种配置 × 正常/中度弱网。客户端自动进行「静止—移动—静止」输入，预热后采集 20 秒，目标 120 FPS，报告仍记录真实帧率。每组使用新进程和新端口，仅清理本脚本创建的进程。中度弱网只注入客户端。约三分钟完成，硬件和启动耗时会影响总时长。

结果为 `TestResults/Timing/summary.json`，每组完整报告也在此目录，日志在 `Logs/Timing`。检查会话成功、起步样本数、回执覆盖和实际频率。脚本不强制某一组必须比另一组快：少量起步样本与系统调度会产生噪声，跨版本或设备比较应增加时长并多轮测试。无图形进程结果不替代两个真实游戏窗口的人工感受验收。

支持的示例命令行：

```text
--net-timing Legacy30|Aligned30|Responsive60
--net-response-metrics true|false
--net-target-fps 120
--net-latency-test --net-report "D:\reports\client.json"
```

不要同时给同一进程启用 `--net-smoke`、`--lobby-test` 和 `--net-latency-test`：它们分别负责独立的自动输入和退出流程。时序对比探针只支持基础玩法示例，不会自动操作大厅准备和开始。

## 5. 接入自己的项目

核心 `MultiplayerSession` 仍默认 30 Hz，且不引用诊断层；示例启动器安装可选 `NetworkTimingController` 并选择 60 Hz。仅添加该组件只能改变会话 Tick，自己的移动代码仍需按玩法需要接入模拟回调，不能自动获得示例时序优化。

1. 在 NetworkManager 同一对象添加 `NetworkTimingController`，在连接前 `Select(NetworkTimingPreset.Responsive60)`。
2. 自己的玩法在生成后订阅 `NetworkManager.NetworkTickSystem.Tick`，在移除时退订。客户端发送输入，服务器按实际 TickRate 的固定步长模拟，不能信任客户端提供的位移或 dt。
3. 使用 Legacy 自定义移动时，参考 `DemoPlayer` 处理乱序/重复指令和数值校验。使用预测模块时由 `PredictedMovement` 管理输入窗口和重放，不再同时订阅另一套移动积分；无输入时停止水平移动，重力继续。示例已安装 `ServerRequestGate`，自建项目按 [账号与请求校验](账号准入与请求校验.md) 显式接入；完整账号后台和网络层洪泛防护不由本模块提供。
4. 若需要显示响应指标，在同一对象添加 `NetworkDiagnostics`（会安装 `NetworkResponseMetrics`），在自己的输入发送、服务器应用确认和本地位置观察点调用测量 API。这些业务埋点不会自动作用于任意游戏。
5. 涉及 Rigidbody/复杂物理时先设计统一物理模拟时钟，不能直接复制本例的 transform 位移到所有物理对象。本例没有改变全局物理设置。

两端 Tick 必须一致，预测世界指纹包含 Tick。当前 0.8.0 示例握手为 **6**：构建器将旧示例配置（版本不高于 5）升级为 6，保留更高的自定义版本；Windows/Linux 两端需使用同版构建。核心 `SessionSettings` 新建默认协议仍为 1，自己的游戏独立维护它，不要只改数字而不更新网络脚本、预制体和配置。

客户端预测、服务器校正和跳跃重放现已实现，接入见 [基础预测](基础移动预测与服务器校正.md) 与 [垂直运动](跳跃重力与地面检测.md)。FPS 射击命中回溯尚未实现。旧 0.4.0 的延迟比较只用于理解时序，不能替代当前预测模式的同协议 On/Off 对比。
