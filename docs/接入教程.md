# 从零接入 Unity 多人联机

当前示例为 0.8.0、协议 6，需重建两端。新增可选 [跳跃、重力与地面检测](跳跃重力与地面检测.md)，包括垂直状态校正与空中恢复；下文带旧版本号的段落保留其历史说明。

适用于 Han Multiplayer `0.8.0`。验证基准为 **Unity 6000.3.26f1、NGO 2.13.3、Unity Transport 2.7.4**。包声明的最低 Unity 版本为 `6000.0`，不代表每个 Unity 6 小版本都已验证；本教程不适用于直接照搬到 Unity 2022.3。

本文中的路径以 Unity 项目根目录为起点。第一次使用请按第 1～5 节操作，先完成两人同机联机，再接入自己的玩法。**本教程仅提供操作说明；当前 Linux 服务器尚未部署。**

## 1. 先理解几个名称

框架负责建立连接、管理会话、处理入房和断线。你的游戏负责角色输入、移动、战斗、背包、UI 和存档。导入包后，还需要把这些玩法改为明确的网络逻辑。

| 名称 | 在本项目里的作用 |
| --- | --- |
| Host / 主机 | 同一进程既运行服务器，也运行一个本地玩家；适合先验证小规模合作玩法 |
| Client / 客户端 | 玩家运行的游戏，连接 Host 或独立服务器 |
| Server / 独立服务器 | 只运行服务器逻辑，没有本地玩家；可构建为 Linux 无图形程序 |
| Relay / 中继 | 转发 Host 与客户端的数据；游戏规则仍由 Host 计算 |
| MultiplayerSession | 框架的连接入口，负责启动、停止、超时、状态和错误 |
| NetworkManager | NGO 的网络管理组件，由 MultiplayerSession 控制生命周期 |
| UnityTransport | 实际发送、接收网络数据的组件 |
| NetworkObject | 让对象拥有可在各客户端对应的网络身份 |
| NetworkBehaviour | 需要使用 RPC、NetworkVariable 等功能的脚本基类 |
| NetworkTransform | 同步位置、旋转、缩放；不会自动把单机移动逻辑改为服务器逻辑 |
| NetworkVariable | 同步持续存在的状态，例如准备状态、生命值；后加入者也能获得当前值 |
| RPC | 向另一端发起一次操作，例如“请求准备”“请求使用道具” |

本示例采用**客户端/服务器架构、服务器权威状态同步**。移动流程是：

```text
本地玩家输入 → RPC 发送移动意图 → 服务器校验并计算位置
                                      ↓
                            NetworkTransform 同步
                                      ↓
                              各客户端显示角色
```

这不是全局确定性帧同步。0.7.0 示例默认安装可选的本地移动预测与服务器校正；下面的最小玩法代码仍用来解释服务器权威流程。预测模块需要显式接入，见 [基础移动预测与服务器校正](基础移动预测与服务器校正.md)，不包含复杂物理回滚或射击命中补偿。

## 2. 先在现有项目跑通两个窗口

### 2.1 打开项目并等待导入

1. 打开 Unity Hub，选择 **Add / 从磁盘添加项目**，选择本框架项目目录。
2. 使用 `6000.3.26f1` 打开。若没有该版本，先在 Hub 安装对应编辑器。
3. 首次打开需要联网下载依赖。等待右下角导入/编译完成。
4. 打开 **Window → General → Console**，先处理所有红色编译错误。编译失败时，后面的工具菜单和组件可能不会出现。
5. 打开 `Assets/MultiplayerDemo/MultiplayerDemo.unity`。如果没有该场景，选择 **Tools → Han Multiplayer → Create or Open Demo** 生成。

**你应该看到：** 场景里有 `Multiplayer` 根对象、平面、相机和灯光。玩家不是预先摆在场景中的，而是在连接成功后由 NGO 生成。

生成菜单不会把已有场景全部重建，但会执行示例升级：为玩家预制体补充缺少的恢复/预测组件，并将不高于 5 的旧示例协议升为 6。它保留更高自定义协议和其他设置；不是修复任意损坏场景的工具。如果配置被改乱，先检查第 4 节，不要依靠再次点菜单覆盖全部配置。

### 2.2 构建第二个窗口

1. 先退出 Play 模式。
2. 选择 **Tools → Han Multiplayer → Build Windows Demo**。
3. 等待 Console 出现构建成功信息。
4. 到 `Builds/Windows` 找到 `MultiplayerDemo.exe`。

保留整个构建目录。复制到另一台电脑时，也要复制 `.exe`、`MultiplayerDemo_Data`、Unity 运行库等全部文件，不能只复制 `.exe`。

### 2.3 编辑器做 Host，程序做 Client

1. 在 Unity 编辑器打开示例场景，点击 Play。
2. 保持 UDP port 为 `7777`，点击 **创建局域网主机**。
3. 等待界面显示“状态：主机在线”（日志为 `State=Host`），出现第一名玩家。
4. 打开刚构建的 `MultiplayerDemo.exe`。
5. 在程序的“服务器 IP”中填 `127.0.0.1`，端口填 `7777`，点击 **通过 IP 加入**。
6. 等待程序显示“状态：客户端在线”（日志为 `State=Client`）。两端应能看到两名玩家。
7. 分别把窗口切到前台，使用 WASD / 方向键或屏幕方向按钮移动。
8. 点击 准备 按钮，观察另一端玩家列表中的准备状态是否变化。

这里两个窗口在同一电脑，所以使用 `127.0.0.1`。只启动一个 Host，第二个窗口点击 通过 IP 加入；如果两个窗口都尝试在同一个监听地址和端口启动 Host，会发生端口占用。

键盘输入依赖旧 Input Manager。只启用新 Input System 的项目可以先使用屏幕按钮；如果确实需要示例中的键盘输入，再在 Player Settings 的 Active Input Handling 中启用 Input Manager 或 Both，并按编辑器提示重启。正式游戏应使用自己的输入方案。

### 2.4 判断是否真正成功

| 操作 | 预期结果 |
| --- | --- |
| Host 启动 | Host 有自己的玩家 |
| Client 加入 | 两端都能看到两名玩家 |
| Client 移动 | Host 窗口能看到 Client 的位置变化 |
| Host 移动 | Client 窗口能看到 Host 的位置变化 |
| 切换 准备 | 对方窗口的状态也变化 |
| Client 点击 断开连接 | Host 保留运行，离开的玩家被移除 |
| Client 主动断开后再次 通过 IP 加入 | 创建新逻辑玩家；主动退出已经撤销旧恢复资格 |
| Client 点击 模拟连接中断（测试重连） | 启用恢复模块时自动重试，以新网络对象恢复原逻辑身份和服务器快照 |
| Host 退出 | Client 收到断线提示；本版没有自动更换房主 |

只看到 `Client` 状态不等于玩法同步完成，至少要检查远端移动和一次状态变化。修改场景、预制体或网络脚本之后，重新构建客户端再比较，避免使用旧程序。

## 3. 导入另一个 Unity 游戏项目

### 3.1 选择一种安装方式

**方式 A：随游戏项目保存整个包，便于团队和多项目固定版本。**

1. 保存目标项目当前工作。
2. 将本项目的整个 `Packages/com.han.multiplayer` 文件夹复制到目标项目的 `Packages` 下，保留全部 `.meta` 文件。
3. 最终路径必须是 `目标项目/Packages/com.han.multiplayer/package.json`，不要再多套一层文件夹。
4. 打开目标项目，等待 Unity 识别嵌入包并解析依赖。

**方式 B：通过磁盘路径引用现有包，便于在本机联调框架源码。**

1. 打开目标项目的 **Window → Package Manager**。
2. 选择 **+ → Install package from disk / Add package from disk**。
3. 选择本项目 `Packages/com.han.multiplayer/package.json`。
4. 安装完成后检查 `Han Multiplayer Framework` 是否出现在已安装列表中。

方式 B 仍然依赖原文件夹位置。移动原目录或把目标项目发给别人后，原本机路径可能不可用。一个目标项目只选一种方式，不要再把包里的 C# 文件复制到 Assets 中，否则可能产生重复类型定义。

### 3.2 核对依赖

| 包 ID | 本项目基准版本 |
| --- | --- |
| `com.unity.netcode.gameobjects` | `2.13.3` |
| `com.unity.transport` | `2.7.4` |
| `com.unity.services.multiplayer` | `2.3.3` |
| `com.unity.services.authentication` | `3.8.0` |
| `com.unity.services.core` | `1.18.0` |
| `com.unity.collections` | `2.6.8` |

依赖由包的 `package.json` 声明。目标项目如果已经固定了其他版本，实际解析结果可能不同；在 Package Manager 和 `Packages/packages-lock.json` 中核对，并处理编译错误后再继续。已有旧版独立 Relay/Lobby/Matchmaker SDK 的项目应先按官方迁移说明处理依赖，避免与 Multiplayer Services 重复安装。参考 [Unity SDK 安装与迁移说明](https://docs.unity.com/en-us/mps-sdk/install-and-upgrade)。

只做 LAN 也会安装当前包声明的云 SDK，但 LAN 运行时不需要关联云项目，不会调用 Relay 登录。

### 3.3 先确认包在新项目中能工作

在目标项目执行 **Tools → Han Multiplayer → Create or Open Demo**，按第 2 节跑一次。这样可以先排除目标项目的依赖或编辑器配置问题，再处理自己的场景。

该菜单生成的资源位于 `Assets/MultiplayerDemo`。这只是演示资源；之后可以继续制作自己的场景。**Windows Demo / Linux Dedicated Server 构建菜单当前都固定构建示例场景，不会自动构建你的游戏。** 自定义游戏的构建见第 10、11 节。

### 3.4 如果自己的代码使用 asmdef

选中自己脚本所在目录对应的 `.asmdef`，在 Assembly Definition References 中按需加入：

| 代码使用了什么 | 要引用的程序集 |
| --- | --- |
| `MultiplayerSession`、`SessionSettings` | `Han.Multiplayer` |
| `NetworkBehaviour`、`NetworkObject`、RPC、NetworkVariable | `Unity.Netcode.Runtime` |
| `UnityRelayProvider`、`RelayProtocol` | `Han.Multiplayer.Relay` |
| 直接操作 `RelayServerData` 等 UTP 类型 | `Unity.Networking.Transport` |
| 临时复用 `DemoPlayer`、`DemoLauncher` 类型 | `Han.Multiplayer.Demo` |

没有自建 asmdef、脚本直接放在普通 Assets 目录时，通常不需要这一步。运行时程序集不要引用 `Han.Multiplayer.Editor`。

## 4. 手动配置自己的联机场景

如果你暂时只想复用示例玩家，可以先复制示例场景再改。下面从空场景开始，逐项解释需要哪些资源。

### 4.1 准备场景和根对象

1. 新建并保存场景，例如 `Assets/MyGame/Scenes/Lobby.unity`。
2. 创建一个空的**根 GameObject**，命名为 `Multiplayer`，不要放在其他对象下面。
3. 给它添加 `NetworkManager`、`UnityTransport` 和 `MultiplayerSession` 组件。
4. 如果添加 `MultiplayerSession` 时依赖组件已经自动出现，直接使用这些组件，不再添加第二份。
5. 需要 Relay 时，在同一对象上添加 `UnityRelayProvider`。
6. 添加自己的相机、灯光和用于观察角色的地面。

初始结构可以是：

```text
Hierarchy（场景对象）
├─ Multiplayer
│  ├─ NetworkManager
│  ├─ UnityTransport
│  ├─ MultiplayerSession
│  └─ UnityRelayProvider（需要 Relay 时添加）
├─ ConnectionUI（第 5 节添加）
├─ Main Camera
├─ Directional Light
└─ Ground

Project（项目资源）
├─ Player.prefab
├─ GameNetworkPrefabs.asset
└─ Lobby.unity
```

`Multiplayer` 是网络管理对象，本身不需要 NetworkObject。整个进程中只保留一个有效的 NetworkManager。相机、HUD、输入控制器等本地对象也不需要全部加 NetworkObject。

### 4.2 制作玩家预制体

1. 在 Hierarchy 创建 Capsule，命名为 `Player`。
2. 在根对象添加 **NetworkObject**。
3. 添加 **NetworkTransform**，Authority Mode 保持 **Server**；位置同步至少包含 X、Z。首次接入可保留默认同步轴和插值配置。
4. 要先验证移动效果，添加包中的 **DemoPlayer**。它会在服务器设置出生位置，并提供屏幕方向键和 准备 按钮。
5. 使用 DemoPlayer 时，根对象需要 Renderer；Capsule 已经有。换成模型时检查 Renderer 的位置，示例脚本不会自动搜索子对象的 Renderer。
6. 把这个 Player 从 Hierarchy 拖入 Project，例如保存到 `Assets/MyGame/Prefabs/Player.prefab`。
7. 删除场景中的临时 Player 实例，保留 Project 中的预制体资源。

**预期结果：** Play 前场景里没有玩家，Host/Client 连接后 NGO 自动生成玩家。

先不要同时保留原来的单机移动脚本和 DemoPlayer，让两套代码都写同一个 Transform。示例 Capsule 的 Collider 也不代表示例移动已经实现碰撞控制；它目前直接修改位置并限制平面边界。

### 4.3 注册网络预制体

1. 在 Project 右键选择 **Create → Netcode → Network Prefabs List**。
2. 命名为 `GameNetworkPrefabs`。
3. 选中该资源，在列表中增加一项，将 Project 中的 `Player.prefab` 拖到该项的 Prefab 字段；Override 保持默认。
4. 选中场景中的 `Multiplayer`，找到 NetworkManager 的网络预制体列表区域，将 `GameNetworkPrefabs` 加入 Network Prefabs Lists。
5. 将同一份 `Player.prefab` 拖到 NetworkManager 的 **Player Prefab** 字段。

如果 Inspector 已经有自动创建的默认 Network Prefabs List，也可以直接使用它，只要玩家预制体在有效列表中注册一次即可。

**Player Prefab 决定加入时自动创建哪个玩家；Network Prefabs List 让各端知道该网络预制体是什么。** 要拖 Project 资源，不能拖场景中的临时玩家实例。客户端和服务器必须使用一致的网络预制体和 NetworkBehaviour 组件顺序。

### 4.4 填写 NetworkManager 与会话参数

不同编辑器皮肤可能把字段放在不同折叠项中，按下面的字段名核对即可。

| 组件 / 字段 | 首次接入填写内容 | 原因 |
| --- | --- | --- |
| NetworkManager / Network Transport | 同一对象上的 UnityTransport | 指定底层传输组件 |
| NetworkManager / Network Topology（如显示） | Client Server | 本框架按 Host/Server 权威模型编写 |
| NetworkManager / Player Prefab | `Player.prefab` | 入房后自动生成玩家 |
| NetworkManager / Network Prefabs Lists | 含玩家的列表资源 | 各端能识别同一个网络对象 |
| NetworkManager / Enable Scene Management | 开启 | 第 7 节同步切场景需要 |
| NetworkManager / Run In Background | 开启 | 桌面窗口失去焦点后仍处理网络 |
| MultiplayerSession / Settings / Application Id | 例如 `my-studio.coop-game` | 标识你的游戏 |
| MultiplayerSession / Settings / Protocol Version | `1` | 不兼容的网络规则变更后递增 |
| MultiplayerSession / Settings / Max Players | `8` | Host 占一个名额，纯 Server 不占 |
| MultiplayerSession / Settings / Connection Timeout Seconds | `30` | 包含 Relay 请求和网络建连的总期限 |
| MultiplayerSession / Settings / Tick Rate | `30` | NGO 网络 Tick，不是渲染帧率或物理频率 |
| MultiplayerSession / Relay Provider | 同一对象上的 UnityRelayProvider，或仅直连时留空 | 为 Relay 提供连接资料 |

ApplicationId 只接受 1～64 个英文字母、数字、点、下划线或连字符。它与 Unity Cloud Project ID 是不同概念；所有参与者的 ApplicationId 和 ProtocolVersion 必须相同。

框架启动时会设置 Network Transport、TickRate、Connection Approval、握手数据及连接端点。端口由调用参数决定，不能仅通过修改 UnityTransport Inspector 的端口来替代 UI/API 中的参数。

框架独占 ConnectionApproval 回调，不要同时运行另一份教程里的审批脚本。若以后需要密码、账号校验或白名单，应在统一准入流程里扩展，而不是覆盖这个回调。

### 4.5 保存场景并加入构建列表

1. 保存 Player 预制体、Network Prefabs List 和当前场景。
2. 打开 **File → Build Profiles**，找到 **Scene List**。
3. 把 Lobby 加入列表并勾选。若当前 Profile 使用自己的覆盖列表，确认实际构建使用的列表也包含它。
4. 第一次只用这个场景，先验证 Host/Client，再增加其他场景。

## 5. 接入连接界面

### 5.1 最快方式：临时使用 DemoLauncher

在 `Multiplayer` 根对象上添加 **DemoLauncher**，就能使用示例的 IP、端口、Relay 房间码和断开按钮。它在运行时读取同一对象上的 MultiplayerSession 和 UnityRelayProvider。

按第 2 节验证，但构建自己的场景时应使用 Build Profiles 的 Build，不能点击固定构建示例场景的 Build Windows Demo 菜单。

**预期结果：** 自己的场景出现连接面板，Host 与 Client 加入后生成你指定的 Player Prefab。

### 5.2 自己的 UI：可直接复制的连接脚本

下面脚本包含一个调试面板，不依赖 Canvas、TMP 或其他 UI 包。它展示了防止重复点击、捕获连接错误、取消连接和订阅状态的完整接法。

1. 新建 `Assets/MyGame/Scripts/MyConnectionUI.cs`，文件名与类名保持一致。
2. 复制下面的代码，等待编译完成。
3. 移除或禁用之前的 DemoLauncher，避免两个入口同时管理同一会话。
4. 新建空对象 `ConnectionUI`，挂上 MyConnectionUI。
5. 将 Hierarchy 的 `Multiplayer` 拖到脚本的 **Session** 字段。
6. Play 后在调试面板创建或加入房间。

```csharp
using System;
using System.Threading.Tasks;
using Han.Multiplayer;
using UnityEngine;

/// <summary>连接界面示例；可直接显示调试面板，也可绑定到自己的 UI。</summary>
public sealed class MyConnectionUI : MonoBehaviour
{
    [SerializeField] MultiplayerSession session;
    [SerializeField] bool showDebugPanel = true;
    string address = "127.0.0.1";
    string portText = "7777";
    string roomCode = "";
    string message = "";
    bool starting; // UI 自己的启动防重入标记。
    bool stopping; // 允许连接等待期间单独执行取消。

    // 绑定引用后订阅事件；不要在 Awake 中抢先调用会话启动 API。
    void OnEnable()
    {
        if (session == null)
        {
            Debug.LogError("请先在 Inspector 给 MyConnectionUI.Session 赋值。", this);
            enabled = false;
            return;
        }
        Application.runInBackground = true;
        session.StateChanged += OnStateChanged;
    }

    // 关闭 UI 只取消订阅，不自动退出房间；离开由 Disconnect 显式发起。
    void OnDisable()
    {
        if (session != null) session.StateChanged -= OnStateChanged;
    }

    // 下列入口可绑定到 UI Button 的 On Click。
    public void HostOnLan() => Run(() => session.StartLanHostAsync(ReadPort()));
    public void JoinIP() => Run(() => session.JoinDirectAsync(address.Trim(), ReadPort()));
    public void CreateRelay() => Run(() => session.StartRelayHostAsync());
    public void JoinRelay() => Run(() => session.JoinRelayAsync(roomCode));

    // 输入框的 On Value Changed 可绑定这些动态 string 方法。
    public void SetAddress(string value) => address = value;
    public void SetPort(string value) => portText = value;
    public void SetRoomCode(string value) => roomCode = value;

    // 使用字符串接收输入，在真正连接前验证端口。
    ushort ReadPort()
    {
        if (!ushort.TryParse(portText, out ushort port) || port == 0)
            throw new ArgumentException("端口必须在 1～65535 之间。");
        return port;
    }

    // async void 只放在事件边界；try 内调用委托，也能捕获同步参数校验错误。
    async void Run(Func<Task> action)
    {
        if (session == null || starting || stopping) return;
        starting = true;
        message = "";
        try { await action(); }
        catch (OperationCanceledException) { message = "连接已取消。"; }
        catch (Exception error)
        {
            message = error.Message;
            Debug.LogWarning(message);
        }
        finally { starting = false; }
    }

    // 不受 starting 阻挡：等待 Relay 或服务器连接时仍可点击取消。
    public async void Disconnect()
    {
        if (session == null || stopping) return;
        stopping = true;
        try { await session.StopAsync(); }
        catch (Exception error) { message = error.Message; Debug.LogWarning(message); }
        finally { stopping = false; }
    }

    // 正式 UI 可在这里更新状态文字；本例直接写日志并由面板读取当前状态。
    void OnStateChanged(SessionState state) => Debug.Log("[MyGame] State=" + state);

    // 调试界面；正式 UI 接好后取消勾选 Show Debug Panel。
    void OnGUI()
    {
        if (!showDebugPanel || session == null || Application.isBatchMode) return;
        bool previousEnabled = GUI.enabled;
        GUILayout.BeginArea(new Rect(20, 20, 360, 460), GUI.skin.box);
        GUILayout.Label("State: " + session.State);
        GUI.enabled = previousEnabled && !starting && !stopping &&
            (session.State == SessionState.Offline || session.State == SessionState.Faulted);
        GUILayout.Label("Server IP");
        address = GUILayout.TextField(address);
        GUILayout.Label("UDP port");
        portText = GUILayout.TextField(portText);
        if (GUILayout.Button("LAN host")) HostOnLan();
        if (GUILayout.Button("Join IP")) JoinIP();
        if (GUILayout.Button("Create Relay room")) CreateRelay();
        roomCode = GUILayout.TextField(roomCode);
        if (GUILayout.Button("Join Relay code")) JoinRelay();
        GUI.enabled = previousEnabled && !stopping;
        if (GUILayout.Button("Cancel / Disconnect")) Disconnect();
        GUI.enabled = previousEnabled;
        GUILayout.Label("Room code: " + session.JoinCode);
        GUILayout.Label(string.IsNullOrEmpty(message) ? session.LastError : message);
        GUILayout.EndArea();
    }
}
```

这个脚本只管理客户端/Host 界面，不提供无图形服务器自动启动；第 10 节给出单独入口。它的 IP、端口和房间码在运行中的面板输入；Relay 的 Profile 和协议则在 UnityRelayProvider 的 Inspector 中提前设置。

### 5.3 换成正式 UI 时如何绑定

如果项目已有 Canvas / Unity UI / TMP：

1. 为按钮的 On Click 添加条目，拖入挂着 MyConnectionUI 的 `ConnectionUI` 对象。
2. 创建局域网按钮选 `MyConnectionUI → HostOnLan()`；加入 IP 选 `JoinIP()`。
3. 创建/加入 Relay 按钮分别选 `CreateRelay()` / `JoinRelay()`；退出按钮选 `Disconnect()`。
4. IP、端口和房间码输入框的 On Value Changed，分别选对应 **Dynamic string** 方法 `SetAddress`、`SetPort`、`SetRoomCode`，不要选固定字符串参数模式。
5. 取消 MyConnectionUI 的 Show Debug Panel，使用 `StateChanged` 更新自己的状态文字。
6. 把启动按钮设为只在 Offline/Faulted 且没有操作进行时可用；取消按钮在 Connecting/Starting 时仍应可用。

`JoinCode` 应在 `await StartRelayHostAsync()` 成功之后展示。输入框不应该直接操作 UnityTransport，UI 统一调用 MultiplayerSession。

## 6. 把自己的玩法接到网络上

### 6.1 先区分输入、规则与表现

| 原单机代码 | 联机后放在哪里 |
| --- | --- |
| 读取本地键盘、手柄、触摸 | 只在 `IsOwner` 的玩家对象上读取 |
| 判定能否移动、攻击、拾取 | 在服务器执行，并检查请求是否合理 |
| 角色位置结果 | 服务器修改，NetworkTransform 同步 |
| 生命值、准备状态、道具数量 | 服务器写入 NetworkVariable 或自己的状态模型 |
| 本地摄像机、HUD、按键提示 | 只为本地玩家启用，不给每个远端对象都启用 |
| 一次性操作请求 | RPC；持续状态另外保存，不靠历史 RPC 回放恢复 |

在 `Awake/Start` 中不能假设网络对象已经生成。依赖 `IsOwner`、OwnerClientId 或同步变量初值的初始化，放到 `OnNetworkSpawn`。在 `OnNetworkDespawn` 取消相关订阅。

复用 DemoPlayer 时，先阅读它的 `Update → MoveRpc → FixedUpdate`：客户端发送方向，服务器限幅、检查无效数值并计算位置。替换自己的控制器时保留这个职责划分；不要让每个客户端都把所有角色移动一遍。

### 6.2 一个独立的“准备状态”完整例子

以下代码用于学习 NetworkVariable 和 RPC，文件名为 `ReadyPlayer.cs`，挂到玩家预制体根对象。它只同步准备状态，不包含移动或名单 UI；如果你已经使用 DemoPlayer 的 准备，可以先阅读而不重复添加。

```csharp
using Unity.Netcode;
using UnityEngine;

/// <summary>对象所有者请求准备，服务器修改状态，所有客户端读取结果。</summary>
public sealed class ReadyPlayer : NetworkBehaviour
{
    public readonly NetworkVariable<bool> Ready = new NetworkVariable<bool>(
        false, NetworkVariableReadPermission.Everyone, NetworkVariableWritePermission.Server);
    float nextToggleTime; // 在服务器限制操作频率。

    public override void OnNetworkSpawn()
    {
        Ready.OnValueChanged += OnReadyChanged;
        // 后加入者已经取得初值，不能只等下一次 OnValueChanged 才更新表现。
        ShowReady(Ready.Value);
    }

    public override void OnNetworkDespawn()
    {
        Ready.OnValueChanged -= OnReadyChanged;
    }

    // 本地 UI 只能操作自己的已生成玩家对象。
    public void RequestToggleReady()
    {
        if (IsSpawned && IsOwner) ToggleReadyRpc();
    }

    [Rpc(SendTo.Server, InvokePermission = RpcInvokePermission.Owner)]
    void ToggleReadyRpc()
    {
        if (Time.unscaledTime < nextToggleTime) return;
        nextToggleTime = Time.unscaledTime + 0.25f;
        Ready.Value = !Ready.Value;
    }

    void OnReadyChanged(bool previous, bool current) => ShowReady(current);

    // 正式游戏在这里更新 UI；日志用来观察其他客户端是否也收到变化。
    void ShowReady(bool value) => Debug.Log("Player " + OwnerClientId + " Ready=" + value);

    // 提供一个测试按钮，避免为了试验状态同步先制作完整 UI。
    void OnGUI()
    {
        if (!IsSpawned || !IsOwner || Application.isBatchMode) return;
        if (GUI.Button(new Rect(20, Screen.height - 60, 240, 40), "Ready: " + Ready.Value))
            RequestToggleReady();
    }
}
```

修改预制体后重新构建第二个客户端。在一端点击按钮，另一端日志应出现对应 OwnerClientId 的 准备 变化；再让一个新客户端加入，它应该直接得到当前值。这同时验证了实时变化和后加入初始同步。

这里的“允许所有者调用”只是网络权限。将来攻击、购买或拾取的 RPC 还必须检查冷却、距离、库存、目标状态等业务条件；客户端应提交意图，由服务器计算结果。

### 6.3 动态生成其他对象

玩家对象已经由 Player Prefab 自动生成，不要在每个客户端的 Start 中再 Instantiate 一份。

箱子、怪物等动态网络对象需要先做成带 NetworkObject 的预制体并注册到 Network Prefabs List，然后由**服务器**实例化并调用 `NetworkObject.Spawn()`。普通 `Instantiate()` 只会产生本地对象。销毁网络对象也应由服务器调用 `Despawn()`，不要仅在某个客户端隐藏后认为所有端都已移除。

相同预制体的 NetworkBehaviour 组件及顺序应在各端一致。服务端构建可用条件编译跳过渲染逻辑，但不要仅在服务端删掉网络行为组件，导致两端网络布局不同。

## 7. 会话生命周期与同步切场景

### 7.1 状态含义与重新连接

```text
Offline → Starting → Connecting → Host / Client / Server
                                    ↓
                                 Stopping → Offline

启动失败或意外断线 → 清理网络 → Faulted
主动取消启动       → 清理网络 → Offline
```

所有接口都在 Unity 主线程调用。连接任务成功只代表本地网络会话建立，不代表玩家预制体、自定义数据或目标场景全部准备完毕；玩法就绪还要结合 OnNetworkSpawn、场景完成事件和自己的资源加载流程。

同一时刻只启动一个会话。切换服务器或模式时，必须按下面的顺序在自己的异步方法中执行，并在调用边界捕获异常：

```csharp
// 先等旧连接完全关闭，再建立新连接；不要把两步并发执行。
await session.StopAsync();
await session.JoinDirectAsync("127.0.0.1", 7777);
```

`StopAsync()` 也可以取消尚未完成的 Relay 请求等待或连接等待。不要在 Unity 主线程调用 `.Wait()` 或 `.Result` 阻塞这些任务。需要外部取消时，可以通过启动方法的 `cancellationToken` 参数传入令牌。

Settings 在启动时复制快照。在线期间修改人数、协议或 TickRate，不会改变当前会话；下次启动才使用新配置。关闭 UI 本身不等于关闭网络，销毁 MultiplayerSession 则会取消启动并请求关闭网络。

### 7.2 从大厅进入游戏

1. 准备 `Lobby.unity` 与 `Game.unity`，将两者加入实际构建使用的 Scene List 并勾选。
2. 确认 NetworkManager 的 Enable Scene Management 已开启。
3. Lobby 初始化唯一的 `Multiplayer` 根对象。NGO 会让根 NetworkManager 跨场景保留，同一对象上的会话也随之保留。
4. Game 场景不要再放另一份 NetworkManager；首次测试始终从 Lobby 启动。
5. 游戏开始按钮只让 Host/Server 发起以下调用。这里是按钮处理函数内部的代码片段，外围仍需 try/catch。

```csharp
// 需要 using Unity.Netcode；调用时 session 必须是已经在线的 Host/Server。
SceneEventProgressStatus result = session.LoadScene("Game");
if (result != SceneEventProgressStatus.Started)
    Debug.LogWarning("场景加载请求未启动：" + result);
```

6. 使用 NGO SceneManager 的场景完成事件确认各端加载情况，再开放玩法操作。返回 Started 只表示请求被接受，不代表所有人加载完毕。
7. 如果 ConnectionUI 随 Lobby 销毁，新场景的 UI 需要重新取得仍存在的会话引用并订阅事件；不要依赖已经销毁的旧 UI。

该接口使用 Single 模式切换。正式玩法还需设计玩家在场景切换中的保留、销毁、出生位置和资源加载流程。大厅示例已通过双端切换和返回验证；自己的场景仍需单独验收。

## 8. 两台电脑或局域网设备联机

先确认两台设备位于可互访的网络，然后在其中一台运行 Host，另一台运行 Client。

| 运行位置 | Client 填写的 IP |
| --- | --- |
| Host 与 Client 在同一电脑 | `127.0.0.1` |
| Host 在另一台局域网电脑 | Host 实际网卡的局域网 IP，例如 `192.168.1.10` |
| 以后连接你的 Linux 服务器 | `192.168.1.111`，前提是服务已部署并启动 |
| 通过公网直连 | 已配置可达入口的服务器公网 IP |

具体步骤：

1. 在 Windows Host 上执行 `ipconfig`，找到当前使用的以太网或 Wi-Fi 网卡 IPv4 地址。
2. 在 Host 启动游戏，点击 创建局域网主机，确认状态为 Host。
3. 把同版本完整客户端构建复制到另一台设备并启动。
4. Client 填 Host 的 IP 和相同端口 `7777`，点击 通过 IP 加入。
5. 若系统防火墙提示，按当前可信网络的设置允许该游戏通信；管理员配置端口时需要关注 **UDP**。
6. 检查 Guest Wi-Fi、AP 隔离、VPN 路由或不同子网是否阻止互访。
7. 按第 2.4 节逐项检查同步和离开重进。

`0.0.0.0` 是监听所有 IPv4 网卡的地址，不是 Client 的连接目标。在 Client 填自己的 IP、另一台机器的 `127.0.0.1`，或把 IP 写成 `192.168.1.10:7777` 都不符合这里的接口用法；地址和端口分开填写。当前 JoinDirectAsync 接受 IP 字面量，不负责解析域名。

SSH 使用的 `22` 端口与游戏 UDP `7777` 无关。能 SSH 登录或能 ping 通，不能证明游戏端口可用；Windows 的 `Test-NetConnection -Port` 检查 TCP，也不能直接作为 UDP 游戏连通的结论。

## 9. Relay 房间码与跨地域联机

### 9.1 准备云项目

1. 在 Unity Hub / 编辑器登录你自己的 Unity 账号。
2. 在 **Edit → Project Settings → Services** 中关联对应组织下的 Unity Cloud 项目。
3. 在该项目的 Unity Dashboard 检查 Authentication / Relay 的服务配置、使用权限及当前套餐/配额。
4. 所有参与者使用关联到同一云项目的构建；不要只在某一台机器换了云项目后继续使用旧客户端。
5. 确认同一对象上已有 UnityRelayProvider，并已赋给 MultiplayerSession 的 Relay Provider 字段。

Unity 云界面的导航可能更新，项目关联和服务安装以 [Multiplayer Services 官方配置说明](https://docs.unity.com/en-us/mps-sdk/tutorials/relay-and-ngo) 为准。本框架已封装初始化、匿名登录和 Relay 数据配置；不必再粘贴另一套直接调用 NetworkManager.StartHost 的云连接脚本。

本框架的 `MultiplayerSession` 是本地会话组件，未接入 UGS 的 Lobby/Matchmaker 或完整 Sessions 大厅功能。安装了 Multiplayer Services 包不代表自动拥有房间列表或匹配系统。

### 9.2 第一次创建与加入

1. 在编辑器的 UnityRelayProvider 设置 Authentication Profile 为 `editor`。
2. 在另一个测试实例使用不同 Profile，例如默认的 `default` 或 `player2`。使用 DemoLauncher 时可在连接面板编辑；使用自己的 UI 时在组件配置或自己的启动流程中设置。
3. 两端都只有桌面/手机玩家时，先保持 Dtls。
4. Host 点击 **创建中继房间**，等待状态变为 Host，再复制显示的 Room code。
5. Client 在房间码输入框填写该码，点击 **通过房间码加入**。
6. 等待 Client 状态，并检查移动和准备状态同步。
7. 再使用不同外网下的两台真实设备重复验证；同机连接成功不能证明跨地域网络已经验证。

Profile 用于区分本地身份缓存，不是玩家昵称或房间名。已经登录后不要直接换 Profile；重启该实例后再配置。游戏如果已经完成账号登录，应让适配器使用相同 Profile 沿用身份。

### 9.3 包含 WebGL 玩家时

在所有参与者上使用 `SecureWebSocket`；DemoLauncher 对应 **WSS 房间**。在创建房间之前设置，桌面主机也选择 WSS。WebGL 构建会强制使用 WSS，而本框架的 WebGL UDP 直连入口会拒绝启动。Unity 的 Web 平台 Relay 接法使用 WSS 和 UnityTransport 的 WebSocket 配置，见 [官方 Web 平台说明](https://docs.unity.com/en-us/mps-sdk/tutorials/relay-and-ngo#note-about-unity-web-platform-support)。

房间码属于当前 Relay 分配，不是永久房间 ID。Host 退出后房间结束，客户端需要加入新创建的房间；当前没有主机迁移。Relay 的费用、可用地区和服务配额以你的云项目当前信息为准。

## 10. 自建 Linux 服务器如何接入

### 10.1 先分清“构建”和“已经运行”

当前项目已生成 Linux x86_64 专用服务端及本地压缩包，但**尚未上传、安装或启动到你的 `192.168.1.111` 服务器**。因此现在直接点击 通过 IP 加入 连接这个地址，不应期待能进入游戏。

本地示例服务端的构建入口为 **Tools → Han Multiplayer → Build Linux Dedicated Server (x64)**。需要安装相同 Unity 版本的 Linux Dedicated Server Build Support；本机已有该模块。结果在 `Builds/LinuxServer`。

仓库中的 `scripts/Build-LinuxServer.ps1` 会构建并打包；`scripts/Package-LinuxServer.ps1` 只对现有产物重新打包，两者都只操作本地。完整压缩包为 `Builds/HanMultiplayer-Linux-x64.tar.gz`。

以后部署并看到 `[Multiplayer] State=Server` 后，同局域网 Client 才填写 `192.168.1.111`、UDP `7777`，点击 **通过 IP 加入**。这里不使用 SSH 用户名、SSH 密码或 Relay 房间码。

`192.168.1.111` 是内网地址。跨地域玩家直连需要公网可达入口、UDP 端口映射/放行，或另外配置的组网方案。当前没有自动把 Linux 独立服务器包装成 Relay 房间的功能。

### 10.2 先用 Windows 程序验证 Server 模型

不部署 Linux，也可以在本机体验“服务器不占玩家名额”。在项目根目录打开 PowerShell：

```powershell
# 当前示例必须已构建；这个窗口启动纯 Server，日志写入 server.log。
& '.\Builds\Windows\MultiplayerDemo.exe' -batchmode -nographics --net-mode server --net-port 7777 -logFile server.log
```

再启动两个普通客户端，分别填 `127.0.0.1:7777` 对应的 IP 与端口字段；或在其他 PowerShell 窗口分别执行：

```powershell
# 此命令只启动一个客户端；再执行一次可以启动第二个客户端。
& '.\Builds\Windows\MultiplayerDemo.exe' --net-mode client --net-address 127.0.0.1 --net-port 7777
```

先停止占用 `7777` 的 Host 再启动 Server。检查两个客户端互相看到玩家，而 Server 本身没有本地玩家。结束后关闭本次启动的游戏进程。

这些 `--net-*` 参数由 **DemoLauncher** 解析，框架核心不会自动解析命令行。自己的项目移除 DemoLauncher 后，需要在自己的启动脚本中实现参数处理。

### 10.3 把自己的场景构建为服务器

两个现有构建菜单固定使用 `Assets/MultiplayerDemo/MultiplayerDemo.unity`。自己的游戏应在 Build Profiles 中选择 Linux Dedicated Server 目标和自己的启动场景，或另写编辑器构建脚本指定场景及 Server 子目标。

服务器没有按钮可点击，启动场景必须有自动启动入口。下面是固定端口的最小例子，保存为 `MyServerBootstrap.cs`，与 MultiplayerSession 挂在同一根对象；不要再同时挂会自动启动的 DemoLauncher。

```csharp
using System;
using Han.Multiplayer;
using UnityEngine;

/// <summary>仅在 Dedicated Server 构建中自动启动；普通客户端不执行。</summary>
[RequireComponent(typeof(MultiplayerSession))]
public sealed class MyServerBootstrap : MonoBehaviour
{
#if UNITY_SERVER
    MultiplayerSession session;

    // Start 时同场景组件的 Awake 已完成，可以调用会话 API。
    async void Start()
    {
        Application.targetFrameRate = 60;
        session = GetComponent<MultiplayerSession>();
        session.StateChanged += OnStateChanged;
        try { await session.StartDedicatedServerAsync(7777); }
        catch (Exception error) { Debug.LogException(error); Application.Quit(1); }
    }

    // 让进程管理器能识别运行中的网络故障。
    void OnStateChanged(SessionState state)
    {
        Debug.Log("[MyGame] State=" + state);
        if (state == SessionState.Faulted) Application.Quit(1);
    }

    void OnDestroy()
    {
        if (session != null) session.StateChanged -= OnStateChanged;
    }
#endif
}
```

该例固定端口为 7777、人数取 Inspector 配置，不读取 SERVER_PORT、MAX_PLAYERS 或 `--net-*`。若要复用现有启动脚本的可配置参数，需要自行加入解析，并同步修改脚本中的可执行文件名。

Dedicated Server 构建会定义 `UNITY_SERVER`；仅给普通 Windows 程序传 `-batchmode -nographics` 不会使该编译分支出现。客户端与服务器要保留相同的游戏 ID、协议、网络预制体和网络脚本布局。

详细的上传、前台运行、systemd 和 Linux 库依赖操作，见完整项目中的 `docs/Linux服务器部署.md`。当前继续保持本地准备，不执行部署。Linux 实机启动及 Windows ↔ Linux 互通仍待以后验证。

## 11. 构建自己的客户端与跨平台检查

### 11.1 自己的游戏构建流程

1. 保存场景、预制体和配置资源。
2. 在 Build Profiles 中选择客户端目标平台并安装对应模块。
3. 确认实际 Scene List 包含你的入口场景和所有通过网络切换的场景。
4. 初次接入使用 Development Build，保留日志便于排错。
5. 通过 Build / Build And Run 构建自己的游戏。示例专用菜单不能代替这一步。
6. 分发完整构建目录，再按第 12 节做双端验收。

| 目标平台 | 需要额外处理 | 当前项目已验证程度 |
| --- | --- | --- |
| Windows | 同版本资源、运行库、防火墙、后台运行 | 已做 Windows 同机多进程连接与同步检查 |
| Linux Dedicated Server | 对应构建模块、架构、系统库、无图形启动入口 | 已构建；未做服务器实机运行 |
| macOS / Linux 客户端 | 构建模块、输入和实机网络 | 未构建及实机验证 |
| Android / iOS | 触控、目标平台网络权限、后台断线处理 | 未实机验证 |
| WebGL | Relay WSS、浏览器环境、平台构建限制 | 未构建及互通验证 |

源码采用可移植 Unity API，不等于所有平台已经互通。移动端进入后台可能被系统暂停或终止。客户端仍存活、持有凭证且未超过服务器保留期时，可由可选恢复模块重连；不保证系统后台唤醒或进程重启恢复。先验证一组真实目标设备，再扩大平台组合。

### 11.2 多个游戏项目如何复用

每个游戏保留独立的 ApplicationId、玩家预制体、场景和玩法代码。连接层继续使用同一包；示例输入、UI 和 DemoPlayer 可以全部替换。

记录并固定包版本、依赖锁文件和构建版本。更新框架后，重新验证旧项目里的 Host、Client、错误处理和目标平台；不要只修改版本字符串就认定新旧网络协议兼容。

## 12. 接入验收清单

建议按顺序做，前一项没通过时先定位问题再进入下一层。

| 检查 | 操作 | 成功标准 |
| --- | --- | --- |
| 编译和引用 | 打开项目，查看 Console | 没有红色编译错误、Missing Script |
| 单端启动 | 创建 LAN Host | Host 状态且生成自己的玩家 |
| 双端连接 | 第二个进程 通过 IP 加入 | Client 状态，两端都有两个玩家 |
| 远端同步 | 两边分别移动和切换 准备 | 另一端看到变化 |
| 主动离开 | Client 断开连接 | Host 保留，离开玩家被清理 |
| 重新加入 | 再次 通过 IP 加入 | 新玩家生成，操作与同步恢复 |
| 主机关闭 | 关闭 Host | Client 显示断线，而不是永久卡在在线状态 |
| 连接失败 | 连接未监听端口 | 在配置期限后报超时，UI 可再次操作 |
| 取消等待 | 连接过程中点击 Cancel | 回到 Offline，可再次启动 |
| 容量 | Host 设置 MaxPlayers=2，加入第三名玩家 | 第三名收到 ROOM_FULL |
| 游戏隔离 | 某客户端改为不同 ApplicationId | 收到 INCOMPATIBLE_GAME |
| 同步切场景 | Host 从 Lobby 加载 Game | 各端完成加载后才进入玩法 |
| 目标网络 | 两台真实设备 / 两个外网 | 同样完成双向移动、状态和断线检查 |

MaxPlayers 允许填写 2～128，只是校验范围。默认 8 人、可填写 128 人都不代表完成过对应人数的性能压测。

现有完整仓库可关闭占用项目的编辑器后运行 `scripts/Verify.ps1`，重现核心测试、示例构建和 Windows 多进程检查。这些测试不会自动覆盖你新增的角色、业务规则或场景；接入后的玩法仍需按表验收。

## 13. 常见问题：按现象定位

| 现象 / 错误 | 优先检查 | 下一步 |
| --- | --- | --- |
| 找不到 Han Multiplayer 菜单或组件 | Console 是否有编译错误；包是否成功安装 | 先修依赖/编译，再查安装路径和 asmdef 引用 |
| `Han.Multiplayer` / `Unity.Netcode` 命名空间不存在 | 脚本所在 asmdef 的引用 | 按第 3.4 节添加实际使用的程序集 |
| 提示 Session 未赋值 | MyConnectionUI 的 Session 字段 | 拖入场景的 Multiplayer 对象，不是脚本文件 |
| `Network startup failed` | 是否两个 Host 占用同一端口、Transport 配置 | 停止本次测试的旧 Host，确认 UDP 监听端口 |
| `Connection timed out` | 先看 Host/Server 是否在线，再查 IP 和端口 | 先同机 `127.0.0.1`，再 LAN，最后外网逐层验证 |
| `INCOMPATIBLE_GAME` | ApplicationId / ProtocolVersion | 对齐配置并重新构建旧客户端 |
| `ROOM_FULL` | Host 也占名额；断开是否完成 | 等待离开清理或在下次启动前调整人数 |
| `NetworkConfig` / prefab mismatch | 旧构建、网络预制体、组件顺序、SDK | 使用同一套资源重建两端，不靠关闭校验掩盖差异 |
| 已连接但没有角色 | Player Prefab、NetworkObject、有效预制体列表 | 检查第 4.2～4.3 节，确认相机也能看到出生位置 |
| 只有本机看到新对象 | 是否只用了 Instantiate | 注册预制体并在服务器调用 Spawn |
| 远端角色也响应本机输入 | 输入脚本缺少 IsOwner 判断 | 只为本地所有者采集输入和启用相机 |
| 移动后被拉回 / 两端争抢位置 | 客户端与服务器都直接写 Transform | 使用一致的 Server 权威模式，让客户端提交输入 |
| 键盘无响应，屏幕按钮可用 | 窗口焦点、输入框焦点、Input System 设置 | 先完成屏幕按钮验证，再适配自己的输入系统 |
| 切换窗口就停顿或掉线 | Run In Background | 开启后台运行；移动端后台需另行处理 |
| `A session is already active` | 重复点击、两个启动组件、未等待 Stop | 统一入口并先 await StopAsync |
| `Assign an IRelayProvider` | Relay Provider 是否为空/类型错误 | 添加 UnityRelayProvider 并赋值 |
| `UGS is already signed in with another profile` | 登录后改变了 Profile | 重启实例，或沿用游戏已登录账号的 Profile |
| UGS 初始化、授权、房间码失败 | 云项目、服务配置、网络、Profile、房间是否仍活跃 | 检查当前 Host 和完整异常，不把旧码当永久房间 |
| WebGL 提示不能 direct UDP | 使用了 通过 IP 加入 / 创建局域网主机 | 使用 Relay WSS，并让参与者配置一致 |
| Client 无权切换场景 | 从客户端调用了 LoadScene | 改由在线 Host/Server 发起 |
| `Add the scene to the build scene list` | 场景名称和实际 Profile 的 Scene List | 加入并勾选后重新构建各端 |
| Linux 地址连不上 | 服务器尚未部署/启动，或 UDP 不可达 | 当前状态下未部署是预期；以后先看 Server 日志 |

排错时同时记录两端的游戏版本、角色（Host/Client/Server）、IP、端口、State 和完整错误文本。只截取最后一句“连接失败”通常不足以判断原因。

Unity 编辑器日志从 Console 查看；示例批处理可用 `-logFile` 明确指定日志路径。项目自动化记录位于 `Logs/Smoke` 和 `TestResults`。不要使用测试开关 `--net-smoke` 启动正常游戏，它会自动移动、执行检查并退出。

## 14. API 速查与代码阅读顺序

| API | 参数 / 使用时机 |
| --- | --- |
| `StartLanHostAsync(port, listenAddress, cancellationToken)` | 默认 UDP 7777、监听 0.0.0.0；当前进程同时是玩家 |
| `JoinDirectAsync(address, port, cancellationToken)` | address 为不带端口的 IP 字面量 |
| `StartDedicatedServerAsync(port, listenAddress, cancellationToken)` | 只启动服务器，不生成本地玩家 |
| `StartRelayHostAsync(region, cancellationToken)` | region 默认为 null，由服务选择；成功后读取 JoinCode |
| `JoinRelayAsync(joinCode, cancellationToken)` | 整理大小写和空白后请求加入 |
| `StopAsync()` | 主动离开或取消启动；等待网络完成关闭 |
| `LoadScene(sceneName)` | 在线 Host/Server 调用，检查返回状态并等待完成事件 |
| `StateChanged` | 更新本地连接状态 UI；订阅后也要读取一次当前 State |
| `PlayerConnected / PlayerDisconnected` | 服务器得到玩家事件；客户端不能据此推断完整大厅名单 |
| `State / IsOnline / LastError / JoinCode` | 用于显示连接状态、原因和当前房间码 |

建议按以下顺序阅读带中文注释的源码：

1. `Runtime/SessionSettings.cs`：配置范围和游戏兼容性握手。
2. `Demo/DemoLauncher.cs`：现成 UI 与命令行如何调用连接层。
3. `Runtime/MultiplayerSession.cs`：启动、取消、超时、准入和断线清理。
4. `Demo/DemoPlayer.cs`：客户端输入、服务器计算、RPC 和状态同步。
5. `Runtime/Relay/UnityRelayProvider.cs`：云服务登录与 Relay 连接资料。
6. `Editor/DemoBuilder.cs`：场景、玩家和预制体列表的自动配置。
7. `Editor/LinuxServerBuilder.cs`：示例 Linux 服务端的构建流程。

以上源码路径相对于 `Packages/com.han.multiplayer`。完整仓库还提供 `docs/兼容性与架构.md`、`docs/验证记录.md` 和 `docs/Linux服务器部署.md`；单独安装包时，可从包内 `Documentation~/index.md` 阅读概览。

当前版本已提供可选的通用大厅模块；跨房间搜索、匹配、账号注册登录后台、主机迁移、进程重启后的角色恢复和完整竞技游戏预测尚未实现。ApplicationId/ProtocolVersion 是兼容检查，不是账号凭证。先完成一个两人小场景、一个服务器判定的操作和一组目标设备验收，再逐步扩展自己的游戏。


新增开发工具见 [网络诊断与弱网测试](网络诊断与弱网测试.md)，包含可选面板、弱网参数、JSON 报告及自动化验证。

通用大厅模块的配置与人工验收见 [通用大厅接入与验收](通用大厅接入与验收.md)。
