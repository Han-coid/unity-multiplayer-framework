# 通用断线重连与状态恢复

当前示例为 0.8.0、协议 6，需重建两端。新增可选 [跳跃、重力与地面检测](跳跃重力与地面检测.md)，包括垂直状态校正与空中恢复；下文带旧版本号的段落保留其历史说明。

此模块位于独立的 `Han.Multiplayer.Recovery` 程序集，可供基础联机、大厅及自己的玩法共用，不依赖 FPS。核心只提供 `ISessionContinuity` 扩展契约；不安装模块时，原来的直连/Relay 生命周期仍可使用。

本版恢复的是**同一服务器进程仍在运行、客户端进程仍持有凭证**的会话。服务器重启恢复、客户端退出后重新启动、Host 迁移、跨服务器迁移和账号后端认证均不在本版范围内。

## 1. 先用两个窗口体验

已重新构建的大厅示例可通过项目目录中的 PowerShell 脚本打开：

```powershell
.\scripts\Start-LobbyAcceptance.ps1
```

1. 两端进入大厅，各自准备，房主开始游戏。
2. 在客户端移动一段距离，然后停止，记住当前位置。不要在 Host 窗口模拟重连；Host 退出会结束整个房间。
3. 在客户端左侧连接面板点击「模拟连接中断（测试重连）」。这是开发工具，绕过主动离场撤销，触发本地网络关闭。它不等同于点击「断开连接」。
4. 客户端显示「等待重试 → 正在重新连接 → 正在恢复服务器状态 → 已恢复原会话」。观察角色位置及当前游戏场景恢复。
5. 在另一窗口观察玩家离线席位、随后重新绑定的连接编号。**连接 ID 和 NetworkObjectId 会改变，逻辑会话身份保持不变。** 本版通过新网络对象恢复原角色快照，不保证旧 GameObject 引用继续有效。
6. 返回大厅后再次验证：昵称保留，准备状态重置。离线玩家保留期间不能开始新一局，房主可以移除该席位，或等待保留期结束。
7. 再次模拟中断，点击「取消重连 / 离开」，确认不再自动尝试。
8. 由房主移除玩家，确认被移除的一端提示原因，且不会自动返回房间。

「模拟连接中断」直接关闭客户端网络，便于人工操作；它没有给所有数据包注入故障。诊断工具的「断网 3 秒」使用真实丢包，但默认 UTP 断开超时较长，3 秒中断可能只触发恢复传输，不会断开会话。需要验证真正超时的流程，可运行第 6 节自动测试，它只在测试进程中将 UTP 超时缩短为 1.5 秒，再模拟双向 100% 丢包 6 秒。

### 1.1 先分清测试的是哪一种恢复

| 操作 | 是否保留恢复资格 | 应观察什么 |
| --- | --- | --- |
| 网络短时丢包但连接未超时 | 原会话仍在线 | 预测可能重新定基，连接 ID 不一定变化 |
| 模拟连接中断 / 实际连接超时 | 默认保留，需仍有有效凭证和席位 | RecoveryStatus 进入重试；新对象绑定原逻辑身份 |
| 点击断开连接 / 取消重连 | 撤销并清除本地凭证 | 不再自动重试；手动加入创建新角色 |
| 房主移出 / 验证拒绝 | 终止恢复；按具体错误处理 | 不应反复自动加入被拒绝的房间 |
| 关闭客户端程序 / 系统杀进程 | 内存凭证丢失 | 不支持跨进程恢复，重新打开不等于同一恢复会话 |
| 关闭 Host / 重启服务器 | 房间或服务器内存租约消失 | 不支持主机迁移或重启后的旧会话恢复 |

默认服务器席位保留 30 秒，客户端重试预算 45 秒。服务器发现断开与客户端发现断开的时刻可能不同，两个计时器也不会同步启动；45 秒预算不能把 30 秒席位延长。先在正常网络验证，再加中度弱网；结束后恢复正常网络，避免上一轮故障参数影响下一轮。

## 2. 在自己的项目安装

### 2.1 网络根对象

在同一个 GameObject 上准备：

- `NetworkManager` 和 `UnityTransport`；
- `MultiplayerSession`；
- 新增 `RecoveryService`。

将 `RecoveryService.Settings` 配置为：

| 设置 | 默认 | 含义 |
| --- | --- | --- |
| AutoReconnect | true | 已取得凭证的客户端意外断线后自动重试 |
| RetentionSeconds | 30 秒 | 服务器观察到断开后保留逻辑角色和席位的期限 |
| RetryWindowSeconds | 45 秒 | 客户端开始自动重连后的总预算；不是服务器保留期 |
| AttemptTimeoutSeconds | 5 秒 | 每次连接尝试的最大时间，还受会话原有连接超时限制 |
| RestoreTimeoutSeconds | 30 秒 | 连接后等待凭证确认与本地玩家生成的最大时间，也受总预算限制 |

各时间必须在 1～300 秒内。运行中的连接使用设置副本，不应通过修改 Inspector 热改本次保留规则。服务器保留期和客户端重试预算是各自计时，服务器可能在客户端总预算用完前就拒绝过期凭证。

服务器和客户端都需要安装此模块；双方不一致会明确拒绝连接。示例启动器默认安装，可用 `--net-recovery false` 关闭（双方一起关闭）。自己的游戏应自行安装组件，不需要使用 DemoLauncher。

### 2.2 玩家预制体

在 NetworkManager 注册的 PlayerPrefab 上添加 `RecoverablePlayer`。已有的 `NetworkObject`、`NetworkTransform` 和玩法脚本继续保留。若设置了 PlayerPrefab 却没有这个恢复组件，启动会明确报错。

本版示例及默认恢复流程采用服务器权威移动；客户端权威 NetworkTransform 的项目需要自行对接对应权威端的恢复流程。

组件自动保存服务器端位置、旋转和缩放，断开时读取同对象上所有 `IPlayerRecoveryState`。重新生成后在 `OnNetworkPostSpawn` 恢复，避免普通出生逻辑再次覆盖快照。

只处理这个玩家对象上注册的状态。客户端拥有的其他对象、掉落物、子弹、外部背包数据库或任务系统不会因为安装组件就自动恢复。持续存在的服务器世界及 NGO NetworkVariable/NetworkList 会按 NGO 的正常连接同步流程发送给重连客户端。

### 2.3 为业务状态提供快照

以服务器维护的生命和弹药为例，在玩家 GameObject 上的业务脚本实现接口。以下片段应与实际战斗脚本合并；所有写入都由服务器执行：

```csharp
using System;
using Han.Multiplayer.Recovery;
using Unity.Netcode;

public sealed class PlayerVitals : NetworkBehaviour, IPlayerRecoveryState
{
    public readonly NetworkVariable<int> Health = new NetworkVariable<int>(100);
    public readonly NetworkVariable<int> Ammo = new NetworkVariable<int>(30);

    // 同一玩家的提供者不能重名；不兼容的存储格式应更换版本并处理迁移。
    public string RecoveryKey => "my-game.vitals.v1";

    public byte[] CaptureRecoveryState()
    {
        if (!IsServer) throw new InvalidOperationException("Only the server captures state.");
        // 此快照仅保存在同一服务器进程内，不作为跨平台传输协议。
        var data = new byte[8];
        Buffer.BlockCopy(BitConverter.GetBytes(Health.Value), 0, data, 0, 4);
        Buffer.BlockCopy(BitConverter.GetBytes(Ammo.Value), 0, data, 4, 4);
        return data;
    }

    public void RestoreRecoveryState(byte[] data)
    {
        if (!IsServer || data == null || data.Length != 8)
            throw new ArgumentException("Invalid vitals snapshot.");
        int health = BitConverter.ToInt32(data, 0);
        int ammo = BitConverter.ToInt32(data, 4);
        if (health < 0 || health > 100 || ammo < 0 || ammo > 30)
            throw new ArgumentException("Vitals are out of range.");
        Health.Value = health;
        Ammo.Value = ammo;
    }
}
```

快照来自服务器业务状态，客户端不能提交角色位置或生命来覆盖它。0.8.0 示例的 `DemoPlayer` 以 `demo.player.v2` 保存 Ready 网络变量和服务器垂直速度；根位置另由 RecoverablePlayer 保存，落地标记按恢复位置和几何重算。Ready 与大厅准备状态不同，大厅准备会明确重置。自己的跳跃角色需要类似速度适配，完整骨架见 [跳跃教程第 5 节](跳跃重力与地面检测.md#5-断线恢复接入)。

每个提供者的键最多 64 个字符，每项最多 16 KiB，每名玩家最多 32 项、总计 64 KiB。数据会复制，不能依赖返回数组继续变动来更新快照。重复键、缺失/多余提供者或恢复异常会使恢复失败，不会悄悄用新角色继续游戏。

本版在断开时保存快照，冻结角色的逻辑状态；断开的网络对象会移除，不继续接受输入。死亡、背包外部变更、离线期间世界变化、原位置被占用等规则，需要你的服务器业务在恢复时校验。为复杂物理角色恢复速度、碰撞状态等，应提供对应状态并按玩法设置，基础位置恢复不等于完整物理回滚。

### 2.4 连接、取消、退出和管理移除

```csharp
// 初次连接仍然使用原来的 API；会话恢复模块会自动提供握手扩展。
await session.JoinDirectAsync("127.0.0.1", 7777);
// Relay 仍使用 session.JoinRelayAsync(joinCode)。

// 用户明确离开：撤销服务器端重连资格，再关闭本机连接。
await session.StopAsync();

// 用户在自动重连过程中取消，等待重试流程和连接一起结束。
await recovery.CancelReconnectAsync();

// 服务器踢人/封禁时使用这个入口，默认撤销凭证；不要直接绕过它断开底层连接。
session.DisconnectPlayer(clientId, "BANNED");

// 只有模拟临时故障等明确需要恢复的管理操作才设为 true。
session.DisconnectPlayer(clientId, "TEMPORARY_DISCONNECT", allowRecovery: true);
```

主动退出会发送离场消息，最多等待 1 秒确认，然后必定关闭本地连接。如果网络完全不可达，服务器不能可靠收到主动离场通知，席位仍可能保留到期限结束。客户端主动退出后会清除凭证，不再自动认领该席位。

自动重连按 1、2、4、5 秒退避（此后最多 5 秒），不在首次连接失败时无休止重试。踢出、凭证无效、过期和协议不兼容等属于终止错误。服务器尚未发现旧连接已断开时，会拒绝并发使用同一身份，客户端可在预算内稍后重试。

自己的账号/封禁系统应在拒绝前撤销对应租约，并按需要取消客户端重试；本模块的内置终止错误包含大厅踢出，不能代替所有业务错误分类。

### 2.5 UI 和业务通知

```csharp
recovery.StatusChanged += status =>
{
    // 将 Waiting / Connecting / Restoring / Recovered / Failed 更新到自己的 UI。
    // 可读取 Attempts、RetryRemainingSeconds、NextAttemptSeconds 和 LastError。
};

recovery.PlayerRestored += (newClientId, sessionId) =>
{
    // 服务器回调：快照已应用。重新关联业务引用，不继续使用断线前的 GameObject。
    // 此时 NGO 的完整连接/场景同步回调可能尚未结束，不在这里假定远端画面已显示。
};
```

恢复完成表示凭证、本地玩家及连接同步条件已满足；后续名单等增量字段仍通过 NGO 正常流式更新，UI 应监听大厅 Changed 等事件，不应假定 Recovered 回调瞬间已包含所有后续增量。

销毁自己的 UI 时解除订阅。`LocalSessionId` 和 `RecoverablePlayer.SessionId` 是逻辑会话标识，不是重连秘密。依赖它们识别玩家，不应把新的 NGO ClientId 当作持久账号 ID。

自己的 asmdef 需要引用 `Han.Multiplayer`、`Han.Multiplayer.Recovery`、`Unity.Netcode.Runtime`。使用基础 MonoBehaviour 脚本而没有自定义 asmdef 时，通常由 Unity 自动处理引用。

## 3. 大厅接入行为

Lobby 模块通过核心契约查询是否为已验证的恢复连接，无需引用 Recovery 程序集：

- 服务器保留名单项和昵称，标记 `IsConnected=false`，撤销准备和加载确认；
- 核心容量计算保留席位，新连接不能占用它，恢复同一席位不会重复计数；
- 已验证恢复连接可重新进入 Playing 中锁定的房间，新玩家仍被锁房规则拒绝；
- Loading/LoadFailed 期间仍拒绝入房，客户端按重试预算等待；
- 当前在线世界的场景和阶段通过 NGO 重新同步，服务器不回退整局进度；
- 回来后名单绑定新的 ClientId，保持昵称，准备重新确认；
- 独立服务器上离线房主的授权转给在线玩家，恢复时不会抢回已转移的权限；
- 过期或被房主移除的离线席位释放。加载屏障检查在线玩家，不让离线记录伪造加载完成。

若大厅在离线期间返回 Waiting，恢复者进入服务器当前的大厅，而不是强行回到断开前的游戏阶段。

## 4. 凭证和存储边界

服务器为会话生成随机 128 位逻辑 ID 和 256 位秘密，以固定长度校验秘密。只允许已连接玩家接收自己的凭证；客户端请求无法指定要踢出或撤销的其他身份。重复连接不能抢走在线角色。

凭证和角色快照仅保存在内存，不写入 PlayerPrefs、诊断报告或控制台。凭证绑定本机的连接目标，换服务器地址或 Relay 房间码会清除旧凭证。服务器重启会清空租约，旧凭证被拒绝；客户端明确退出也会清除凭证。

这些随机凭证证明“持有本次会话的恢复权”，不证明账号身份。直连 UDP 本身没有加密，不能保证凭证在不可信网络上的保密；正式公网项目应接入受保护的传输及自己的账号认证，Relay 默认 DTLS/WSS 可用于保护对应传输路径。不要将凭证放到昵称、公开 NetworkVariable、截图或日志里。

## 5. 版本和兼容性

本轮示例协议版本升为 **3**：LobbyPlayerState 新增连接状态，玩家预制体新增 RecoverablePlayer。旧二进制必须重建，两端包、网络预制体、Tick 配置和恢复模块配置保持一致。生成器只将自带示例的默认协议 1/2 升为 3，保留更高的自定义版本；自己的游戏有不兼容网络修改时仍要升级自己的协议版本。

Linux 基础示例专用服务器已在本地重新编译并打包，包含当前协议与恢复模块；它仍不包含大厅 Entry/Lobby/Game 场景。本轮不部署或执行 Linux 运行测试。Windows 直连的自动测试不能替代 Linux、移动设备、WebGL 或 Relay 的实机验收；Relay 重试路径已接入原有 JoinRelayAsync，但需要有效云项目、身份和仍存活的 Relay Host 才能验证。

## 6. 自动验证

先构建基础与大厅 Windows 示例：

- **Tools → Han Multiplayer → Build Windows Demo**；
- **Tools → Han Multiplayer → Build Windows Lobby Demo**。

然后运行：

```powershell
.\scripts\RecoveryTest.ps1
# 或单独一组
.\scripts\RecoveryTest.ps1 -Case Recover
.\scripts\RecoveryTest.ps1 -Case Expire
.\scripts\RecoveryTest.ps1 -Case Cancel
.\scripts\RecoveryTest.ps1 -Case Leave
.\scripts\RecoveryTest.ps1 -Case Kick
.\scripts\RecoveryTest.ps1 -Case Lobby
```

测试覆盖：真正超时后自动重试、保留席位不能被新玩家占用、逻辑身份一致但网络 ID 改变、位置与 Ready 恢复、无重复角色、过期不自动创建新角色、取消后不再重试、意外关闭过程中主动退出仍能撤销恢复、踢出撤销、Playing 场景及名单昵称恢复、拒绝新玩家中途加入。

结果位于 `TestResults/Recovery/summary.json`，详细日志在 `Logs/Recovery`。本轮失败会清除旧汇总，不能把上次 PASS 当作本轮通过。脚本仅管理自己的本机测试进程，不修改防火墙或远端服务器。

原有 `scripts/Verify.ps1`、`LobbyTest.ps1` 和 `WeakNetworkTest.ps1` 继续使用。自动断网测试不替代人工窗口的手感和界面验收。
