# 通用大厅：接入与人工验收

当前示例为 0.8.0、协议 6，需重建两端。新增可选 [跳跃、重力与地面检测](跳跃重力与地面检测.md)，包括垂直状态校正与空中恢复；下文带旧版本号的段落保留其历史说明。

大厅位于独立程序集 `Han.Multiplayer.Lobby`，不依赖 FPS、Demo、诊断或 Unity 云服务。可以在 LAN、直连独立服务器、Relay 会话上使用；本次实际验证以本机 Windows 直连为主。它是游戏内联网大厅，不提供跨服务器的房间搜索、匹配或 UGS Lobby 服务。

## 1. 示例资源与窗口

Unity 菜单：

- **Tools → Han Multiplayer → Create or Open Lobby Demo**：生成并打开入口场景。
- **Tools → Han Multiplayer → Build Windows Lobby Demo**：构建到 `Builds/LobbyWindows/LobbyDemo.exe`，保留原来的简单联机示例。

示例采用三个场景：

| 场景 | 职责 |
| --- | --- |
| `Assets/MultiplayerLobbyDemo/Entry.unity` | 唯一网络根对象与连接界面，开始时离线加载 Lobby |
| `Assets/MultiplayerLobbyDemo/Lobby.unity` | 大厅内容，不放另一份 NetworkManager |
| `Assets/MultiplayerLobbyDemo/Game.unity` | 游戏内容，不放另一份 NetworkManager |

入口中的网络根对象及服务器动态生成的大厅对象跨场景保留，因此返回 Lobby 不会重新创建第二套网络管理器。**从 Entry 启动 Play 或构建，不要直接从 Game 场景开始测试。**

## 2. 人工验收：一台电脑两个窗口

在项目根目录的 PowerShell 中执行：

```powershell
.\scripts\Start-LobbyAcceptance.ps1
```

脚本打开昵称为“房主”“玩家”的两个可交互窗口，自动连接本机 UDP 7777；不会自动准备、开始游戏或踢人。端口被其他程序占用时会提示，不会结束其他进程。可使用 `-Port 7788` 换端口。

若只导入了 UPM 包，新项目不会出现这个仓库脚本或已有 exe。先用菜单生成并构建大厅示例，手动运行两个 LobbyDemo.exe：第一个创建主机，第二个填写 127.0.0.1 和相同端口加入。运行现成仓库脚本前关闭上一轮窗口；若提示缺少程序，使用 Build Windows Lobby Demo，而不是基础示例的 Build Windows Demo。

用 Alt+Tab 切换窗口，或 Win+左右方向键将窗口分放两侧。右侧是大厅面板，左侧是连接面板；诊断面板默认隐藏，可在大厅面板中打开。示例按钮和状态提示已使用简体中文，常见错误保留原始代码便于排查。

| 步骤 | 由谁操作 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| 1 | 两端观察 | 查看右侧名单 | 两端看到同一份“房主”“玩家”名单；同一玩家的 ID 在两端一致，两个玩家自身的 ID 不同；房主有管理权限 |
| 2 | 玩家窗口 | 输入新昵称，点击 更新昵称 | 两端名单都更新；不会修改 Host 的名称 |
| 3 | 房主窗口 | 两人未准备时点击 开始游戏 | 显示 PLAYERS_NOT_READY，仍在 Lobby |
| 4 | 房主窗口 | 修改最小人数或勾选规则，再点 保存房间规则 | 两端看到新规则，所有人的 准备 被清除 |
| 5 | 两端 | 分别点击 准备 | 两端名单都显示两人 READY |
| 6 | 房主窗口 | 点击 开始游戏 | 先显示 Loading / 加载状态，再统一进入 Playing；Scene 显示 Game |
| 7 | 两端 | 移动角色 | 只有进入 Playing 后可操作；两端看到位置变化 |
| 8 | 房主窗口 | 点击 全员返回大厅 | 两端返回 Lobby / Waiting；准备和加载标志重置；名单与昵称保留 |
| 9 | 房主窗口 | 在“玩家”行点击 移出 | 玩家显示 KICKED_FROM_LOBBY 并断开；房主名单移除该玩家 |
| 10 | 玩家窗口 | 在左侧点击 通过 IP 加入 再加入 | 出现新的连接 ID，可重新设置昵称和准备；没有自动封禁；被移除的凭证已撤销，手动重新加入会创建新角色 |
| 11 | 玩家窗口 | 主动 断开连接 | Host 保留，名单及时移除 Guest |
| 12 | 房主窗口 | 关闭 Host 窗口 | 在线 Guest 报断线，不会自动迁移服务器 |

人数最少默认 2，容量默认 4；Host 也算一名玩家。Require every player ready 包括房主自身。Allow joining after game starts 默认关闭。规则修改会撤销所有人的准备，因此改完后需要再次 准备。

0.8.0 游戏场景中还可按空格或点击“跳跃（按一次）”。先完成大厅表中的场景进出，再按 [跳跃验收表](跳跃重力与地面检测.md) 检查平台、顶板和重连。大厅 Waiting 阶段不能移动/跳跃属于预期，不能因此判定预测失效。进入游戏后只有当前获得焦点的窗口接收键盘操作。

### 检查进行中锁房

1. 两端进入 Playing，并保持 Allow joining after game starts 关闭。
2. 另开一个 `LobbyDemo.exe`，输入 Host IP 和相同端口，点击 通过 IP 加入。
3. 新客户端应显示 `GAME_IN_PROGRESS`，已有两名玩家继续游戏。
4. 返回大厅后，在房主规则中允许中途加入，重新准备并开始，再测试第三个客户端。
5. 允许中途加入时，NGO 先同步当前游戏场景；服务端完成连接后才把新玩家加入名单并标记已加载。

Loading 和加载失败等待处理期间始终锁房；允许中途加入不会绕过加载屏障。

### 两台电脑验收

把**整个** `Builds/LobbyWindows` 文件夹复制到另一台 Windows 电脑。主机运行 Host，另一台在左侧填主机真实局域网 IP 与端口并 通过 IP 加入，再重复上表。跨设备结果需要人工确认；同机通过不能代表防火墙、网络权限或外网已经验证。

验收日志保存在 `Logs/LobbyAcceptance/本次时间/host.log`、`guest.log`。若发现问题，请记录操作步骤、哪个窗口、右侧 Phase、左侧 State 和错误文字；不要只报告“连接失败”。

## 3. 接入自己的游戏

1. 安装基础包，按基础接入教程配置 NetworkManager、UnityTransport、MultiplayerSession 和 Player Prefab。
2. 在网络根对象上添加 **LobbyService**，整个会话只使用一个大厅服务。
3. 制作 `LobbyRoom.prefab`：根对象添加 **NetworkObject** 与 **LobbyRoom**。不要把它预先摆在 Lobby / Game 场景中；服务器会动态生成。
4. 把该预制体注册到所有参与端相同的 Network Prefabs List，并赋给 LobbyService 的 **Room Prefab**。服务启动前也会检查注册，推荐在编辑器中显式注册以便审查。
5. 配置 LobbyService.Settings 的 Lobby Scene、Game Scene、Minimum Players、Require All 准备、Allow Late Join 和 Scene Load Timeout Seconds。
6. Lobby / Game 必须不同，且都在实际构建使用的 Scene List 中。开启 NGO Enable Scene Management。
7. 容量取 MultiplayerSession 本次启动的 MaxPlayers 快照；运行中不能通过修改 Inspector 临时扩大容量。需要改容量时先停止会话。
8. 自己的 asmdef 引用 `Han.Multiplayer.Lobby`；直接访问 FixedString / NetworkList API 的代码还需 `Unity.Collections`、`Unity.Netcode.Runtime`。
9. 在 UI 中等 `LobbyService.Room` 非空且 `IsSpawned` 后读取同步状态、发送请求。
10. 玩法只在 Phase 为 Playing 时接受操作；服务器也必须检查，不能只禁用客户端按钮。示例 DemoPlayer 已演示这一点。

基础会话层通过 `IConnectionAdmissionRule` 调用可选的大厅锁房规则，仍保留游戏 ID、协议与容量检查。大厅不覆盖核心 ConnectionApproval 回调；自定义认证也应接到统一扩展入口中。

模块应在连接前安装并配置。要移除或禁用大厅服务，先停止会话；不支持在线热移除仍在使用的大厅对象。

## 4. 数据与 API

| 对象 / 字段 | 含义 |
| --- | --- |
| `LobbyService.Room` | 当前同步大厅对象；断线清理后为空 |
| `LobbyService.LocalNickname` | 本机连接后发送的初始昵称 |
| `LobbyRoom.Players` | 服务器维护的连接名单，含 ClientId、Nickname、IsReady、IsLoaded |
| `LobbyRoom.LeaderId` | 当前有权管理房间的玩家连接 ID |
| `LobbyRoom.Rules` | 最少/最多人数、是否要求全员准备、是否允许中途加入 |
| `LobbyRoom.Phase` | Waiting、Loading、Playing、LoadFailed |
| `LobbyRoom.TargetScene / LoadError` | 当前加载目标及失败原因 |
| `LobbyRoom.Changed` | 同步数据变化通知；初次订阅后也要立即读取当前值 |
| `LobbyRoom.Feedback` | 本地请求反馈；OK 或拒绝原因，仅发送给请求者 |

这些网络字段默认只有服务器能写。自定义 UI 可以调用：

```csharp
// 放在自己的 UI 方法中；先检查 service.Room != null && service.Room.IsSpawned，并处理异常。
service.Room.RequestNickname("PlayerA");
service.Room.RequestReady(true);
// 下面请求只有当前房主有权执行，服务端会再次校验权限。
service.Room.RequestRules(2, true, false);
service.Room.RequestStartGame();
// 游戏开始或加载失败后，可请求统一返回大厅。
service.Room.RequestReturnToLobby();
// 使用名单中的目标连接 ID；不能踢自己或 Host。
service.Room.RequestKick(targetClientId);
```

不要将这些示意调用在同一帧全部连续执行。UI 操作应等待反馈或同步状态，避免在尚未生成、加载中或刚更新规则时继续提交后续操作。示例对昵称与准备请求做了 0.25 秒服务端限频。

主动断开和重新加入仍使用 `await session.StopAsync()`、`JoinDirectAsync` 等基础 API：主动离场撤销恢复资格，新连接创建新身份。0.5.0 示例默认启用可选恢复模块，意外断线则保留离线席位及昵称，重连后绑定新的连接 ID 并恢复逻辑身份；此凭证不是账号认证。

## 5. 开始游戏和加载失败

开始时服务器检查：发起者是房主、仍处于 Waiting、没有已批准但未完成的连接、达到最少人数，以及要求的全员准备条件。

通过后先锁房进入 Loading，再调用 NGO 同步加载。IsLoaded 取自服务端观察到的 SceneEvent，不接受客户端直接把自己改成已加载。只有加载整体完成、仍在线玩家都完成且没有超时，才进入 Playing。

场景缺失或请求未被 NGO 接受时，不会强行进入游戏，会显示拒绝并恢复原阶段。加载超时/失败进入 LoadFailed，玩法保持禁用，房主可以请求返回 Lobby。此版本不提供踢掉慢客户端后自动继续游戏的策略。

独立服务器不占玩家名额：第一位远端玩家成为大厅房主，离开后授权给下一位在线玩家。这只是**大厅管理权限转移**，不是 Host 主机迁移。专用服务器也可由可信管理代码调用 `StartGameOnServer()`。

## 6. 自动化验证

已有大厅构建时执行：

```powershell
.\scripts\LobbyTest.ps1
```

脚本以三个独立进程检查：同一份名单/昵称、非房主的真实 RPC 被拒绝、准备校验、全员加载后进入 Game、进行中拒绝新连接、返回 Lobby、踢人原因及移除名单。结果在 `TestResults/lobby.json`，日志在 `Logs/Lobby`。

规则单元测试和编辑器运行时测试属于现有测试程序集，可用 `scripts/Verify.ps1` 运行。完整仓库已提供生成后的大厅场景；如果是刚单独导入源码包的项目，应先生成大厅示例再运行依赖这些资源的 PlayMode 测试。

自动化验证不替代最终窗口操作、真实两台设备、Relay、移动平台和 Linux 服务端联调。本次不涉及服务器部署。
